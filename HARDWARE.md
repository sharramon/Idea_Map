# Target Hardware

Idea_Map has two hardware deployment phases with very different constraints. The embedding layer must be designed as a dual path from the start.

---

## Phase 1 targets — constrained (near-term)

### Meta Quest 3
- **Chipset:** Snapdragon XR2 Gen 2
- **NPU:** ~10 TOPS
- **RAM:** 8GB LPDDR5
- **OS:** Android-based (sideloading possible)
- Running local embedding models is possible but tight — not practical for always-on use

### Snap Spectacles (4th gen)
- **Chipset:** Snapdragon AR1 Gen 1
- **OS:** Lens OS (Lens Studio)
- **ML:** SnapML supports ONNX — but constrained to sub-10MB models, vision workloads (YOLOv7-tiny, MobileNet), 224×224 input
- Text embedding models are technically the right format (ONNX, INT8) but the hardware simply isn't powerful enough for NLP transformer inference at useful speed
- Designed for lightweight computer vision, not text encoding

**Constraint summary:** Neither device can reliably run local embedding model inference at query time. The device should hold pre-computed data only and route any inference to the cloud.

---

## Phase 2 target — capable (long-term)

### Snapdragon Reality Elite
Source: https://www.qualcomm.com/xr-vr-ar/products/snapdragon-reality-elite

| Component | Detail |
|-----------|--------|
| NPU | **48 TOPS** — 160% improvement over XR2+ Gen 2 |
| GPU | Up to 60% improvement |
| CPU | Up to 30% improvement |
| Display | Up to 4.4K per-eye at 90 FPS |
| Memory bandwidth | Increased (exact figure not published) |
| Thermal | Up to 12°C cooler under load |
| Battery | Up to 20% longer at equivalent workload |
| Computer vision | Hardened EVA block with dedicated HW acceleration |

**Device configurations:**
- **All-in-one** — glasses are self-contained
- **Disaggregated** — glasses + separate compute puck (puck handles heavy compute, glasses handle display/sensors)
- **Tethered** — paired to phone or PC
- OST and VST both supported

The disaggregated config is key — the puck is not head-worn, so thermals/battery constraints are much looser.

48 TOPS is comparable to a flagship Android phone (Snapdragon 8 Gen 3). Qualcomm explicitly lists LLMs and large vision models as first-class use cases. At this level, on-device embedding inference is comfortable:

| Model | Format | Est. size | Feasibility on Reality Elite |
|-------|--------|-----------|------------------------------|
| `nomic-embed-text-v1` | INT8 ONNX | ~67MB | Comfortable |
| `bge-base-en-v1.5` | INT8 ONNX | ~110MB | Comfortable |
| `bge-small-en-v1.5` | INT8 ONNX | ~8MB | Trivially easy |

## Dual-path embedding architecture

Because Phase 1 devices cannot run local inference, the embedding layer must support two paths:

### Path A — OpenAI (build first)
All ML computation is external. The device holds data only.

```
Desktop:  ingestion → OpenAI embeddings API → embeddings.json
                                                     ↓ sync
Device:   query text → OpenAI embeddings API → query vector → local cosine search over synced vectors
```

- Device stores `embeddings.json` (pre-computed vectors — just arrays of numbers, no model needed)
- Cosine search is pure arithmetic — trivial on any device including Spectacles
- Query embedding requires a network round-trip to OpenAI (~100–200ms)
- Works on Quest 3, Snap Spectacles, anything with internet access

### Path B — Local model (build later, for Phase 2)
No external API calls. Model runs on-device.

```
Desktop:  ingestion → local ONNX model → embeddings.json
                                               ↓ sync
Device:   query text → on-device ONNX model → query vector → local cosine search
```

- Requires capable NPU (Reality Elite class)
- Model format: INT8 ONNX (compatible with Hexagon NPU via ONNX Runtime Mobile)
- Recommended model: `nomic-embed-text-v1` INT8 (~67MB)
- Fully offline — no network needed at query time

### Why this split works

Pre-computed embeddings are just numbers. The device never needs to run the model that generated them — it only needs to compute dot products. Cosine search over 1000 entries at 768 dimensions is ~0.8M multiplications — microseconds on any modern CPU, trivial even on Spectacles.

The only time a model is needed:
1. **Ingestion** — generating vectors for new entries (always on desktop)
2. **Query** — embedding the user's search string at query time

Path A routes (2) to OpenAI. Path B runs (2) locally. (1) never moves to the device.

### Implementation

The `EmbeddingClient` interface abstracts the provider. Switching paths is a config change:

```
IDEA_MAP_EMBEDDINGS=true
IDEA_MAP_EMBEDDING_PROVIDER=openai   # or: local
IDEA_MAP_EMBEDDING_MODEL=text-embedding-3-small
```

Vectors must be generated by the same model throughout — you cannot mix OpenAI and local vectors in the same `embeddings.json`. A provider switch requires re-embedding all entries (`embed-backfill`).

## Longer-term: could the LLM extraction pipeline move on-device?

Possibly, in disaggregated mode on Reality Elite. Small quantized LLMs that could run on the puck:
- Gemma 3B INT4 (~2GB)
- Llama 3.2 3B INT4 (~2GB)
- Phi-3 Mini INT4 (~1.8GB)

The 3-pass pipeline at full quality needs Sonnet/Haiku class — not feasible locally yet. But a lightweight local pass for quick capture, with desktop pipeline used for quality backfill, is plausible.

**Do not hardcode the assumption that LLM calls are always remote.**
